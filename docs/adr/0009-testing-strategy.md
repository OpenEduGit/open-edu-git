# ADR-0009 — استراتژی تست: Vitest (واحد + یکپارچگی سبک)، E2E به تعویق

- **Status:** ACCEPTED
- **Date:** 2026-10-31

## Context

تا P3 صفر تست خودکار وجود داشت؛ همهٔ اعتبارسنجی دستی بود (curl + مرورگر). برای مهاجرت PostgreSQL (P5) و ادامهٔ توسعه، به تور رگرسیون نیاز است — اما بدون هزینهٔ راه‌اندازی E2E سنگین در همین گام.

## Decision

- **Vitest** به‌عنوان رانر تست (سازگار با tsconfig/alias `@/*`، سریع، بومی TS).
- **سطوح در P4:**
  - `tests/unit/**` — توابع خالص `src/lib` (diff، format، امضای بلیت HMAC).
  - `tests/integration/auth.test.ts` — فقط جریان احراز هویت، علیه **سرور dev گذرا** روی `TEST_PORT` (پیش‌فرض 3002 — هرگز 3000؛ 3001 روی ماشین نگهدارنده توسط docker-proxy اشغال است) با **دیتابیس SQLite دورریز** در /tmp و seed به‌عنوان fixture واحد.
- **Playwright (E2E) به P4.6**، یکپارچگی کاملِ تمام endpointها به **P4.5**، آستانهٔ پوشش به P5+ موکول شد.
- پوشش فعلاً **فقط اطلاعاتی** است (`thresholds: {}`).

## Consequences

**(+)** CI یک job تست سریع (< ۹۰ ثانیه لوکال، ~۲-۳ دقیقه CI)؛ رگرسیونِ منطق سهم‌بندی/فرمت/امضا گرفته می‌شود؛ seed.ts به‌عنوان منبع یگانهٔ دادهٔ تست تثبیت شد.

**(-)** روت‌های غیر auth تا P4.5 بدون تور یکپارچگی‌اند؛ E2E (کلاس زنده، تخته، UI) تا P4.6 پوشیده نمی‌شود؛ پوشش routeها در گزارش v8 دیده نمی‌شود (server در پروسهٔ جدا اجرا می‌شود — پوشش آنها فقط از راه تست‌های integration واقعی P4.5 معنا پیدا می‌کند).

## نکتهٔ اجرایی (درس P4)

سرور گذرا از **کپی ایزولهٔ اپ** در /tmp اجرا می‌شود: Next 16 در dev یک flock انحصاری روی `<app>/.next/dev/lock` می‌گذارد و `bunx next` هنگام راه‌اندازی، درخت node_modules را بازنویسی می‌کند که از مسیر هاردلینک‌ها به node_modules مخزن هم propagate می‌شود. راه‌حل: کپی اپ (`.next` مستقل) + هاردلینک node_modules + spawn باینری next **مستقیم** (بدون bunx) — تست‌شده که بعد از اجرای تست، مخزن دست‌نخورده می‌ماند (`git status -- src/` خالی، mtimeهای node_modules/next پایدار).

## Migration plan

- **P4.5:** integration برای pamphlets/fork/MR، wallet/slots/sessions، courses — همان الگوی سرور گذرا، هر حوزه یک فایل، serial.
- **P4.6:** Playwright (دو context مرورگر برای کلاس زنده)، ورود به CI.
- **P5+:** آستانهٔ پوشش (پیشنهاد: ≥۷۰٪ برای src/lib، ≥۶۰٪ برای API) بعد از مهاجرت PostgreSQL.
