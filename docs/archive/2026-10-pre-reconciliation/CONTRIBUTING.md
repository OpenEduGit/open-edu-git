## 🛤️ مسیرهای مشارکت

### 🧑‍🏫 معلم هستم، می‌خواهم جزوه بگذارم

حتی اگر با گیت و گیت‌هاب راحت نیستی، چند مسیر ساده پیش پایت است:

1. **فرم گوگل (ساده‌ترین راه):**  
   برو به [این لینک](https://forms.gle/WAziARJ78LHCs7cj6) و جزوه‌ات را همراه با چند مشخصهٔ ساده (پایه، درس، فصل، سبک تدریس) بارگذاری کن.  
   ما خودمان آن را وارد کتابخانه می‌کنیم و **نام تو به عنوان مؤلف** برای همیشه کنارش می‌ماند.

2. **ایمیل یا تلگرام:**  
   اگر فایلت بزرگ‌تر از ۱۰ مگابایت است، مستقیم به ایمیل یا تلگرام ما بفرست. در پیامت بنویس: پایه، درس، فصل، و هر توضیحی که دوست داری.

3. **خودت مستقیم در گیت‌هاب (اختیاری):**  
   اگر کمی با گیت آشنا شدی، می‌توانی با یک Pull Request جزوه‌ات را اضافه کنی:
   - مخزن را Fork کن.
   - فایل جزوه را در پوشهٔ `pamphlets/` (یا طبق ساختار پوشه‌بندی) قرار بده.
   - یک فایل `info.md` با نام، پایه، درس و غیره در کنارش بگذار.
   - یک Pull Request باز کن و ما بررسی می‌کنیم.

> 🧠 **نکته:** تمام محتوا تحت مجوز CC BY-SA 4.0 منتشر می‌شود. یعنی نامت می‌ماند و هیچ‌کس نمی‌تواند بدون ذکر نامت از آن استفادهٔ تجاری کند. برای اطمینان، هنگام ارسال، چک‌باکس «با انتشار آزاد موافقم» را در فرم می‌زنی.

### 👀 معلم هستم، می‌خواهم جزوه‌ها را بازبینی کنم

بازبینی تو ارزشمندتر از طلاست!  

- به [بخش Discussions](https://github.com/OpenEduGit/open-edu-git/discussions) برو و نظرت را دربارهٔ جزوه‌های موجود بنویس.
- می‌توانی پیشنهاد بدهی: «اینجا یک مثال از زندگی واقعی کم است»، «این توضیح برای بچه‌های ضعیف‌تر مناسب‌تر است اگر …».
- اگر خطای علمی یا نگارشی دیدی، یک [Issue جدید](https://github.com/OpenEduGit/open-edu-git/issues/new?template=bug_report.md) باز کن (الگوی «گزارش اشکال محتوایی» را پر کن).

برای بازبینی نه گیت لازم است، نه برنامه‌نویسی. فقط کافی است نظرت را بنویسی.

### 💻 برنامه‌نویس هستم، می‌خواهم کد بزنم

قدم‌های اول:

1. **محیط توسعه را آماده کن:**  

   ```bash
   git clone https://github.com/OpenEduGit/open-edu-git.git
   cd open-edu-git
   docker-compose up
   ```

   جزئیات بیشتر در [DEVELOPMENT.md](./DEVELOPMENT.md) (به‌زودی).

1. **یک Issue برای خودت پیدا کن:**  
   به [بخش Issues](https://github.com/OpenEduGit/open-edu-git/issues) برو و برچسب‌های زیر را نگاه کن:
   - `good first issue` – مناسب برای اولین مشارکت
   - `help wanted` – دست‌یاری فوری می‌طلبد
   - `backend` / `frontend` / `docs` و غیره.
   قبل از شروع، در آن Issue کامنت بگذار و بگو «من این را انجام می‌دهم» تا کسی موازی کاری نکند.

1. **کدت را بنویس و Pull Request بده:**
   - از شاخهٔ `main` یک شاخهٔ جدید بساز: `feature/your-feature` یا `fix/short-description`.
   - تغییراتت را commit کن (پیام‌ها به فارسی یا انگلیسی، اما مختصر و گویا).
   - یک Pull Request به `main` باز کن.
   - در توضیحات PR بنویس «چه کردی» و «چرا». اگر Issue مرتبطی دارد، شماره‌اش را لینک کن.

1. **منتظر بازبینی بمان:**  
   نگهبانان پروژه (Maintainers) ظرف چند روز بررسی می‌کنند. اگر تغییری خواستند، با روی باز انجام بده.

**قراردادهای کدنویسی:**  
هنوز در حال شکل‌گیری است. فعلاً:

- برای فرانت‌اند: از کامپوننت‌های React با TypeScript استفاده کن، رابط کاربری کاملاً RTL باشد.
- برای بک‌اند: API ها RESTful و مستند (Swagger) باشند.
- حتماً برای فیچرهای جدید تست بنویس.
- اطلاعات حساس (کلیدهای API، رمزها) را در کد کامیت نکن.

### 🎨 طراح یا تایپیستم، چطور کمک کنم؟

- **طراحان گرافیک / UI/UX:**  
  ما به لوگو، صفحه‌آرایی جزوه‌ها، نمودارهای تعاملی و بهبود تجربهٔ کاربری نیاز داریم.  
  ایده‌هایت را در Discussions مطرح کن یا فایل‌های طراحی‌ات را در Issueها به اشتراک بگذار.

- **تایپیست‌های عزیز:**  
  بسیاری از جزوه‌های ناب دست‌نویس هستند. می‌توانی با تبدیل آنها به Markdown یا LaTeX، گنجینه‌ای آزاد بسازی.  
  جزوه‌های آماده برای تایپ را در Issueهای برچسب‌دار `typist-needed` پیدا می‌کنی.  
  فایل نهایی را مثل یک جزوهٔ معمولی Pull Request کن.

### 📣 همهٔ ما: گزارش اشکال و پیشنهاد ویژگی

- **گزارش اشکال:**  
  اگر در پلتفرم، جزوه‌ای، یا هر بخش پروژه مشکلی دیدی، یک [Issue جدید](https://github.com/OpenEduGit/open-edu-git/issues/new?template=bug_report.md) باز کن.  
  بگو: مشکل چه بود؟ کجا دیدی؟ چه انتظاری داشتی؟ (هرچه دقیق‌تر، بهتر)

- **پیشنهاد ویژگی:**  
  ایده‌ای برای بهتر شدن داری؟ [فرم پیشنهاد](https://github.com/OpenEduGit/open-edu-git/issues/new?template=feature_request.md) را پر کن. حتی یک خط توضیح هم ارزشمند است.

## ⚙️ فرایند توسعه برای برنامه‌نویسان

1. **شاخه‌ها (Branches):**
   - `main` – شاخهٔ پایدار (فقط از طریق Pull Request ادغام می‌شود).
   - شاخه‌های توسعه: `feature/*`، `fix/*`، `docs/*`.

2. **Pull Request:**
   - اطمینان حاصل کن که تغییراتت روی آخرین نسخهٔ `main` اعمال می‌شود (rebase کن).
   - عنوان PR خلاصه و توصیفی باشد.
   - اگر کارت نیمه‌تمام است، از Draft PR استفاده کن.

3. **بازبینی و ادغام:**
   - حداقل یک نگهبان پروژه باید تأیید کند.
   - تا زمانی که بحث فنی باز است، ادغام انجام نمی‌شود.
   - پس از ادغام، شاخهٔ feature حذف می‌شود.
